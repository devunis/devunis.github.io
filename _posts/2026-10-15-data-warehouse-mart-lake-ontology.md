**웨어하우스·마트·레이크·레이크하우스는 데이터의 저장·정제·활용 구조를, 온톨로지는 개념과 관계의 의미를 다룹니다.** 이 글에서는 쇼핑몰 예제로 각 개념과 연결 방식을 설명합니다.

기존 DB 제품 비교 시리즈와 별도로 읽을 수 있는 개념 정리 글입니다. 공식 문서 확인 기준일은 2026년 10월 15일입니다.

## 🏢 데이터 웨어하우스: 분석을 위한 통합 데이터

데이터 웨어하우스(Data Warehouse, DW)는 여러 원천의 데이터를 분석 목적으로 통합하는 저장소와 그 운영 체계입니다. 업무 시스템의 데이터를 그대로 모으는 데서 끝나지 않고 식별자·타입·업무 기준을 맞춰 분석에 사용할 수 있도록 합니다. [AWS 공식 설명](https://aws.amazon.com/what-is/data-warehouse/)

쇼핑몰의 주문 시스템과 결제 시스템을 예로 들면, 고객 ID 형식이나 시간대, 취소 상태의 표현이 다를 수 있습니다. 이를 정리해야 “지난달 고객별 순매출”을 일관되게 계산할 수 있습니다.

### 업무용 DB와의 차이

업무용 DB에서는 주문 생성이나 재고 변경처럼 적은 레코드를 자주 읽고 수정합니다. 웨어하우스에서는 많은 기록을 읽어 기간별·지역별로 집계하는 작업이 중요합니다. 무거운 분석을 분리하면 업무 요청과 자원 경쟁을 줄일 수 있습니다.

예를 들어 다음처럼 분석 모델을 구성할 수 있습니다.

| 분석 테이블 | 담을 내용 |
| --- | --- |
| 주문 항목 팩트 | 주문 항목별 수량·금액·할인 |
| 고객 차원 | 고객의 분석 속성 |
| 상품 차원 | 상품·카테고리 속성 |
| 날짜 차원 | 날짜·월·분기·공휴일 정보 |

이는 스타 스키마를 활용하는 예시이며, 모든 웨어하우스가 이 구조를 사용해야 하는 것은 아닙니다. 과거 분석의 재현을 위해 고객·상품 속성의 변경 이력도 고려해야 합니다.

Snowflake, BigQuery, Amazon Redshift 같은 플랫폼으로 구축할 수 있습니다. 제품 기능의 범위는 넓어지고 있으므로 제품명 하나를 특정 아키텍처와 완전히 동일시하지 않습니다.

## 🛍️ 데이터 마트: 특정 업무를 위한 분석 영역

데이터 마트(Data Mart)는 마케팅·재무·영업처럼 특정 부서나 주제의 분석 요구에 집중한 데이터 영역입니다. **단순히 용량이 작은 DB를 뜻하지는 않습니다.** [AWS 공식 설명](https://aws.amazon.com/what-is/data-mart/)

| 마트 | 제공할 데이터 | 답할 질문 |
| --- | --- | --- |
| 마케팅 마트 | 캠페인·유입·전환·광고비 | 어느 캠페인의 전환율이 높은가? |
| 재무 마트 | 결제·환불·정산 | 환불을 반영한 정산 금액은 얼마인가? |
| 상품 마트 | 상품·판매·재고 | 어떤 상품을 보충해야 하는가? |

마트는 웨어하우스에서 데이터를 받아 구성하는 **종속형**, 원천 시스템에서 직접 구성하는 **독립형**, 두 방식을 결합하는 **혼합형**으로 설명할 수 있습니다.

별도 서버가 필수인 것은 아닙니다. 같은 분석 플랫폼에서 테이블·뷰·스키마와 권한으로 업무 영역을 나눌 수도 있습니다.

주의할 점은 부서마다 지표 정의가 달라지는 것입니다. 마케팅의 매출은 주문 금액, 재무의 매출은 환불·취소를 반영한 금액이라면 같은 이름의 지표가 다른 값을 냅니다. 마트별 목적은 존중하되 계산 기준·갱신 시점·담당자를 명시해야 합니다.

## 🌊 데이터 레이크: 다양한 데이터를 담는 기반

데이터 레이크(Data Lake)는 정형·반정형·비정형 데이터를 다양한 형태로 저장하고 처리하는 기반입니다. 원천에 가까운 데이터를 보존해 새로운 분석이나 모델 학습에 재활용할 수 있습니다. [AWS 공식 설명](https://aws.amazon.com/what-is/data-lake/)

| 데이터 | 가능한 저장 형태 | 활용 예 |
| --- | --- | --- |
| 주문 기록 | CSV, Parquet | 집계·재처리 |
| 클릭 이벤트 | JSON, Parquet | 행동 분석 |
| 상품 이미지 | 이미지 파일 | 이미지 검색·모델 학습 |
| 고객 상담 | 텍스트·오디오 | 상담 분석 |

레이크는 원본 데이터만 저장하는 곳이 아닙니다. 원본 영역과 정제 영역, 활용용 데이터를 함께 관리할 수 있습니다.

### Schema-on-read는 스키마가 없다는 뜻이 아니다

웨어하우스는 저장 전에 구조를 맞추는 schema-on-write, 레이크는 읽을 때 구조를 해석하는 schema-on-read로 자주 설명합니다. 이는 경향을 이해하기 위한 구분입니다. 실제 레이크에서도 스키마·타입 검증을 수행하고, 현대 웨어하우스도 반정형 데이터를 다룹니다.

Amazon S3, Azure Data Lake Storage, Google Cloud Storage 같은 저장 기반을 사용할 수 있습니다. 다만 객체 저장소에 파일을 올렸다는 사실만으로 활용 가능한 레이크가 완성되지는 않습니다.

데이터 검색을 위한 카탈로그, 소유자·출처, 접근 권한, 품질 검사, 보존·삭제 정책이 필요합니다. 관리 없이 파일만 쌓이면 무엇이 최신이고 신뢰할 수 있는지 알기 어려운 데이터 늪(Data Swamp)이 됩니다.

## 🏠 데이터 레이크하우스: 레이크 위의 테이블 관리·분석

레이크하우스(Data Lakehouse)는 레이크의 저장 기반에 테이블 관리와 분석 기능을 결합하는 아키텍처입니다. SQL 분석과 데이터 엔지니어링·ML이 데이터를 함께 활용하도록 구성할 수 있습니다. [Databricks 공식 설명](https://docs.databricks.com/aws/en/lakehouse/)

핵심은 파일만 저장하는 것을 넘어 데이터 변경을 안전하게 기록하고, 일관된 테이블 상태를 조회하며, 스키마 변경과 이력을 관리하는 것입니다. 지원 범위는 테이블 포맷·엔진·카탈로그의 조합에 따라 달라집니다.

### 제품과 구성 요소를 구분하기

| 역할 | 예시 | 담당하는 일 |
| --- | --- | --- |
| 저장 기반 | S3, Azure Data Lake Storage, Google Cloud Storage | 데이터·메타데이터 파일 보관 |
| 데이터 파일 포맷 | Parquet | 열 단위 데이터 표현·저장 |
| 테이블 포맷·관리 계층 | Apache Iceberg, Delta Lake | 파일을 테이블로 관리하고 변경·스냅샷 추적 |
| 처리·질의 엔진 | Spark, Trino | 데이터 변환·SQL 실행 |
| 카탈로그·거버넌스 | AWS Glue Data Catalog, Unity Catalog 등 | 테이블 식별·메타데이터·정책 관리 |
| 통합 플랫폼 | Databricks 등 | 여러 계층을 연결한 운영·분석 환경 |

[Apache Iceberg](https://iceberg.apache.org/)는 분석용 테이블 포맷이고, [Delta Lake](https://docs.delta.io/index.html)는 테이블의 트랜잭션·메타데이터 등을 관리하는 오픈소스 프로젝트입니다. 둘 다 독립적인 SQL 실행 엔진과 동일한 개념은 아닙니다. Parquet 파일 하나도 테이블 전체의 트랜잭션을 보장하는 관리 계층과 구분해야 합니다.

레이크하우스를 도입해도 작은 파일 정리, 동시 쓰기, 카탈로그 일관성, 엔진 간 기능 호환성, 비용 관리는 남습니다. 모든 업무에서 기존 웨어하우스를 반드시 대체하는 정답은 아닙니다.

## 🧠 온톨로지: 데이터의 의미를 명시하는 모델

온톨로지(Ontology)는 도메인의 개념과 관계, 그 의미를 규정하는 공리 등을 명시적으로 표현한 모델입니다. 저장 위치를 결정하는 아키텍처와는 다른 관점입니다. OWL은 온톨로지를 표현하는 W3C 표준 언어 중 하나입니다. [W3C OWL 2 개요](https://www.w3.org/TR/owl2-overview/)

쇼핑몰 도메인이라면 다음 요소를 표현할 수 있습니다.

| 요소 | 예시 |
| --- | --- |
| 클래스·개념 | 고객, 주문, 상품, 디지털 상품 |
| 관계·객체 속성 | 고객이 주문을 생성한다, 주문이 상품을 포함한다 |
| 데이터 속성 | 주문의 생성 시각, 상품의 이름 |
| 실제 개체 | 고객 C001, 주문 O1001, 상품 P001 |
| 계층·공리 | 모든 디지털 상품은 상품이다 |

온톨로지가 `디지털 상품은 상품의 하위 클래스`라고 정의하고 P001이 디지털 상품이라는 사실이 있다면, 이를 지원하는 추론 과정에서 P001도 상품이라고 도출할 수 있습니다. 명시한 사실과 공리로 얻는 결과이며 임의의 사실을 생성하는 것은 아닙니다. [W3C OWL 2 입문](https://www.w3.org/TR/owl-primer/)

### 스키마·택소노미·지식 그래프와의 차이

| 개념 | 초점 | 예시 |
| --- | --- | --- |
| DB 스키마 | 데이터 구조·타입·저장 규칙 | orders.customer_id는 고객 테이블을 참조 |
| 택소노미 | 분류와 계층 | 상품 → 전자제품 → 노트북 |
| 온톨로지 | 개념·관계·공리의 의미 | 디지털 상품은 상품의 한 종류 |
| 지식 그래프 | 개체와 사실을 연결한 지식 표현 | 고객 C001이 주문 O1001을 생성 |
| 그래프 DB | 그래프 데이터를 저장·조회하는 시스템 | Neo4j, Neptune |

이 경계가 항상 완전히 분리되는 것은 아닙니다. 스키마에도 업무 의미가 담길 수 있고, 지식 그래프가 온톨로지 자체를 포함할 수도 있습니다. 중요한 것은 **의미 모델, 실제 사실, 저장 시스템의 역할을 구분**하는 것입니다.

### 온톨로지와 검증 규칙도 구분

OWL은 알려지지 않은 사실을 곧바로 거짓으로 보지 않는 개방 세계 가정을 사용합니다. 속성이 빠졌다고 일반적인 DB의 NOT NULL 위반처럼 처리한다고 가정하면 안 됩니다.

“모든 주문에는 고객 ID가 있어야 한다” 같은 데이터 품질 검증은 DB 제약 조건이나 별도의 검증 체계와 함께 설계합니다. RDF 그래프의 조건 검증에는 [W3C SHACL](https://www.w3.org/TR/shacl/) 같은 언어를 사용할 수 있습니다. 온톨로지의 추론과 입력 데이터 검증은 목적이 다릅니다.

온톨로지는 파이프라인의 마지막에 반드시 붙는 저장소가 아닙니다. 여러 데이터 계층을 해석하는 공통 의미 모델로 활용할 수 있습니다.

다만 온톨로지를 만들었다고 고객 ID가 자동으로 통합되거나 매출 계산 기준이 저절로 일치하지는 않습니다. 식별자 매핑, 단위·시간대 변환, 지표 정의, 출처 추적을 실제 데이터와 연결해야 합니다.

---

## ✅ 어떤 요구에서 검토할까?

| 요구 | 먼저 검토할 개념 |
| --- | --- |
| 여러 업무 시스템의 지표를 일관되게 분석 | 데이터 웨어하우스 |
| 특정 부서에 필요한 데이터만 제공 | 데이터 마트 |
| 다양한 원천 데이터를 보존하고 재활용 | 데이터 레이크 |
| 레이크 기반 테이블을 SQL·분석·ML에서 함께 활용 | 데이터 레이크하우스 |
| 시스템마다 다른 개념·관계를 명시적으로 연결 | 온톨로지 |

실제 선택에서는 데이터 최신성, 권한, 품질, 재처리, 운영 비용을 함께 확인해야 합니다. 구조를 선택하는 일과 데이터의 의미에 합의하는 일은 모두 필요하며, 어느 한쪽만으로 신뢰할 수 있는 분석 환경이 완성되지는 않습니다.
