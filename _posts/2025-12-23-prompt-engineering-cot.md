프롬프트 설계는 모델이 수행할 과제, 입력 자료, 제약과 결과 형식을 명확하게 만드는 작업입니다. 긴 지시나 특정 문구를 붙이는 것만으로 품질이 항상 좋아지는 것은 아닙니다.

## 🎯 먼저 명세를 명확하게

```text
과제: 아래 변경 사항의 코드 리뷰를 작성한다.
입력: 변경 코드와 관련 테스트.
기준: 재현 가능한 결함과 요구사항 누락을 우선 확인한다.
출력: 문제 위치, 발생 조건, 영향, 검증 방법.
근거가 부족한 부분은 확정하지 말고 확인할 사항으로 표시한다.
```

이는 설명용 프롬프트입니다. 실제 코드를 읽고 실행하는 도구·권한이 없다면 모델이 테스트를 수행했다고 가정하지 않습니다.

## 🧠 Chain-of-Thought의 의미

CoT 연구는 중간 풀이가 포함된 예시 등으로 추론 과제를 돕는 접근을 다룹니다. 연구에서의 특정 모델·과제 결과가 모든 모델과 서비스에서 동일하게 재현되는 것은 아닙니다.

사용자에게는 검증 가능한 계산, 가정, 근거와 간결한 설명을 요청할 수 있습니다. 출력된 긴 설명 자체를 실제 내부 처리의 증거나 정답 보증으로 보지 않습니다.

## 🔀 여러 후보 비교

여러 답안을 생성해 비교하거나, 최종 답의 일치 여부를 집계하는 방법을 검토할 수 있습니다. 같은 모델의 후보들이 같은 오류를 반복할 수 있으므로 다수결만으로 사실을 확정하지 않습니다. 추가 호출의 비용·지연도 고려합니다.

## 🧪 품질을 측정하기

| 항목 | 확인 방법 |
| --- | --- |
| 정확성 | 정답 데이터·테스트·검토 기준 |
| 요구 충족 | 출력 형식과 제약 검사 |
| 근거 | 주장과 입력 자료의 일치 |
| 비용·지연 | 같은 조건의 실제 실행 기록 |

평가 데이터를 고정하고 프롬프트 변경 외의 조건을 유지합니다. 과거 글의 정답률 향상 수치는 실행 기록이 없어 제거했습니다.

## ✅ 실전 원칙

자료와 지시를 구분하고 외부 문서 안의 명령을 그대로 따르지 않도록 합니다. 예시를 추가할 때는 실제 과제와 맞는지 확인합니다. 결과를 길게 설명하도록 만드는 것보다 성공·실패를 판정할 기준과 도구를 갖추는 일이 중요합니다.
