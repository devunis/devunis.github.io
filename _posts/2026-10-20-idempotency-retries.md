주문 버튼을 눌렀는데 화면에 타임아웃이 표시되었습니다. 다시 누르면 주문이 두 개 생길까요? **응답을 못 받았다는 사실과 서버가 처리하지 않았다는 사실은 다릅니다.**

이 글에서는 멱등성과 재시도를 주문 생성 예시로 살펴봅니다. 2026년 10월 20일 확인한 표준·공식 자료를 참고했으며, 실제 결제 시스템의 운영 경험이나 성능을 주장하는 글은 아닙니다.

## 응답만 사라질 수도 있다

<figcaption>처리는 성공했지만 호출자는 모르는 상황</figcaption>

문제는 주문뿐 아니라 이메일 발송, 포인트 지급, 외부 서비스 호출에서도 발생합니다. 그래서 재시도는 실패 처리와 함께 설계해야 합니다.

## 멱등성은 같은 응답을 뜻하지 않는다

멱등성은 동일한 요청을 여러 번 적용해도 **서버에 의도된 효과가 한 번 적용한 경우와 같다는 성질**입니다. 응답 본문·상태 코드·로그 기록이 모두 같아야 한다는 뜻은 아닙니다.

| 요청 의도 | 반복했을 때의 효과 | 판단 |
| --- | --- | --- |
| 알림 설정을 꺼진 상태로 지정 | 계속 꺼진 상태 | 멱등하게 설계 가능 |
| 알림 설정을 현재 상태의 반대로 변경 | 켜짐·꺼짐 반복 | 일반적으로 비멱등 |
| 잔액을 1,000원 증가 | 요청마다 증가 | 일반적으로 비멱등 |
| 특정 주문 ID를 삭제 | 삭제된 상태 유지 | 멱등하게 설계 가능 |

HTTP에서 GET 등 안전한 메서드와 PUT·DELETE는 멱등한 의미로 정의됩니다. DELETE가 첫 번째에는 성공, 다음에는 찾을 수 없음으로 응답하더라도 멱등성을 위반한다고 볼 수는 없습니다. POST에는 멱등성이 기본 보장되지 않지만 애플리케이션 계약을 통해 중복 처리를 막을 수 있습니다. [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)

메서드 이름만 맞추면 충분한 것도 아닙니다. GET에서 주문을 생성하는 구현은 GET의 안전한 의미를 어기는 설계입니다.

## 멱등성 키로 같은 작업을 식별한다

재시도할 때마다 새 키를 만들면 서버는 다른 작업으로 볼 수 있습니다. 클라이언트는 **하나의 논리적 작업에 같은 키를 재사용**해야 합니다.

```http
POST /orders HTTP/1.1
Host: api.example.com
Content-Type: application/json
Idempotency-Key: order-attempt-a7

{"productId":"book-4","quantity":1}
```

이 헤더는 예시 API의 계약입니다. 키 보관 기간·오류 재현·동시 요청 처리는 제공자마다 다릅니다. 예를 들어 Stripe는 멱등성 키와 재시도 파라미터를 비교하는 정책을 문서화하고 있습니다. 그 동작을 모든 API의 공통 규칙으로 일반화하면 안 됩니다. [Stripe 멱등 요청](https://docs.stripe.com/api/idempotent_requests)

## 조회 후 저장만 하면 생기는 경쟁 상태

동시에 들어온 요청 A와 B가 둘 다 “키 없음”을 확인하고 주문을 만들 수 있습니다. 메모리의 집합이나 단순한 사전 조회만으로는 여러 서버의 중복 실행을 막기 어렵습니다.

다음은 저장할 정보의 개념 예시입니다.

| 필드 | 목적 |
| --- | --- |
| 사용자·작업 범위 + 키 | 다른 사용자나 작업의 키와 구분 |
| 요청 내용 지문 | 같은 키로 다른 내용을 보내는 경우 탐지 |
| 상태 | 진행 중·완료·실패 등의 처리 정책 |
| 결과 또는 결과 참조 | 재요청에 기존 처리 결과 제공 |
| 생성·만료 시각 | 보관·정리 정책 적용 |

같은 작업을 점유하는 과정에는 DB의 유일성 제약이나 원자적 연산 같은 동시성 제어가 필요합니다. 유일성 제약은 조합 키에도 적용할 수 있습니다. [PostgreSQL 제약 조건](https://www.postgresql.org/docs/current/ddl-constraints.html)

<figure class="article-diagram diagram-alternatives">
<figcaption>같은 키를 만났을 때의 분기</figcaption>
<ol><li>새 키 → 원자적으로 점유하고 작업 시작</li><li>완료된 키 + 같은 요청 → 저장된 결과 제공</li><li>진행 중인 키 → 계약에 따라 대기 또는 진행 중 응답</li><li>같은 키 + 다른 요청 → 충돌로 거절</li></ol>
</figure>

키의 존재는 인증을 대체하지 않습니다. 기존 결과를 반환할 때도 호출자의 권한과 키 범위를 확인합니다.

## DB 트랜잭션 밖의 효과는 어떻게 할까?

주문 저장과 키의 완료 기록을 같은 DB 트랜잭션으로 묶을 수 있다면 중간 상태를 줄일 수 있습니다. 하지만 외부 결제 호출·메일 발송까지 로컬 트랜잭션이 되돌려 주지는 않습니다.

외부 제공자의 멱등성 지원, 처리 상태 조회, 정합성 복구, 트랜잭셔널 아웃박스 같은 별도 설계를 검토해야 합니다. 키 하나를 붙였다는 이유로 모든 시스템에서 “정확히 한 번 실행”이 보장되는 것은 아닙니다.

보관 기간이 지난 키로 재시도하면 새 작업으로 처리될 수도 있습니다. 클라이언트의 재시도 기간과 서버의 키 보관 기간을 맞추고, 오래된 불확실한 작업은 상태 조회로 확인하는 방법도 필요합니다.

## 재시도에도 예산이 필요하다

일시적인 장애에는 재시도가 도움이 되지만, 무제한 재시도는 부하를 키울 수 있습니다. 총 대기 시간과 횟수를 제한하고, 간격을 늘리는 backoff와 요청이 동시에 몰리지 않게 하는 jitter를 검토합니다. 여러 계층이 각각 재시도하면 실제 호출 수가 증폭될 수도 있습니다. [AWS 재시도 설계](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

입력 오류나 권한 오류는 같은 요청을 그대로 반복해도 해결되지 않습니다. 실패 원인과 작업의 중복 안전성을 함께 확인해야 합니다.
