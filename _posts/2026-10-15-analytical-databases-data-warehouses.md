> 데이터베이스 종류와 대표 제품을 비교하는 7편 시리즈의 7편입니다. 각 제품명은 공식 소개 또는 문서로 연결됩니다.

주문 한 건을 정확하게 저장하는 일과 수억 건의 주문에서 지역별 매출을 계산하는 일은 자원 사용 방식이 다릅니다. 이 글에서는 대량 스캔·집계와 분석 SQL을 중심으로 대표 제품 7개를 비교합니다.

---

## 📊 OLTP와 OLAP

| 구분 | OLTP: 온라인 트랜잭션 처리 | OLAP: 온라인 분석 처리 |
| --- | --- | --- |
| 예시 | 주문 생성, 재고 변경, 결제 기록 | 월별 매출, 사용자 행동 집계 |
| 접근 범위 | 비교적 적은 레코드를 자주 조회·변경 | 많은 레코드를 읽고 조인·집계 |
| 중요한 점 | 동시성, 지연, 트랜잭션 | 스캔·압축, 병렬 처리, 집계 비용 |

많은 분석용 제품은 열 단위 저장·처리로 필요한 컬럼을 읽고 압축 효과를 얻습니다. 하지만 관계형이라는 데이터 모델과 분석용이라는 용도는 배타적이지 않습니다. DuckDB도 SQL과 관계형 기능을 제공하는 분석용 DB입니다. [DuckDB 설계 안내](https://duckdb.org/why_duckdb)

데이터 웨어하우스는 여러 원천의 데이터를 분석 목적으로 통합하는 체계·플랫폼입니다. 아래 제품들은 기능 범위가 서로 다르며, 모두 같은 배포 형태의 DB 엔진은 아닙니다.

## 🧮 분석용 제품별 특징

| 제품 | 특징·강점 | 검토할 사용처 | 주의점 |
| --- | --- | --- | --- |
| [ClickHouse](https://clickhouse.com/docs/get-started/about/intro) | 컬럼 지향 SQL 분석 DB, 대량 집계와 이벤트 분석 | 제품 분석, 로그·이벤트 집계 | 정렬 키·파티션·데이터 엔진과 갱신 방식 설계 |
| [DuckDB](https://duckdb.org/why_duckdb) | 프로세스 안에서 실행되는 분석 DB, SQL과 파일 분석 | 로컬 데이터 분석, Python·R, Parquet 탐색 | 임베디드 실행과 동시 쓰기·공유 요구를 구분 |
| [Snowflake](https://docs.snowflake.com/en/user-guide/intro-key-concepts) | 클라우드 데이터 플랫폼, 저장·컴퓨팅 분리와 virtual warehouse | 조직의 데이터 통합, 분석 업무 분리 | warehouse 크기·실행 시간·데이터 이동 비용 관리 |
| [Google BigQuery](https://cloud.google.com/bigquery/docs/introduction) | 서버리스 분석 플랫폼, 분산 SQL 실행 | 대규모 데이터 분석, Google Cloud 연계 | 과금 모델, 파티션·클러스터링, 스캔량 관리 |
| [Amazon Redshift](https://docs.aws.amazon.com/redshift/latest/dg/welcome.html) | AWS 관리형 데이터 웨어하우스, 프로비저닝·서버리스 구성 | AWS 데이터 통합과 BI | 배포 방식별 자원·비용, 테이블·쿼리 설계 |
| [Apache Druid](https://druid.apache.org/docs/latest/design/) | 분산 분석 DB, 시간 기반 세그먼트와 빠른 집계 | 스트리밍 이벤트 대시보드, 대화형 분석 | 수집·세그먼트·보존 정책과 운영 구성 관리 |
| [Apache Pinot](https://docs.pinot.apache.org/) | 분산 실시간 OLAP, 스트리밍·배치 수집과 인덱스 | 사용자에게 직접 제공하는 저지연 분석 | 인덱스·분할·수집 지연과 클러스터 구성 검증 |

### ClickHouse와 DuckDB

둘 다 분석 SQL을 다루지만, ClickHouse는 서버형·분산 분석 구성으로 검토하고 DuckDB는 프로세스 안에 넣어 사용하는 분석 엔진이라는 구조 차이가 큽니다. 사용자가 여러 명인지, 데이터가 어디에 있는지, 별도 서버 운영이 필요한지를 먼저 봅니다.

### Snowflake·BigQuery·Redshift

세 제품 모두 클라우드 분석 환경에서 비교할 수 있습니다. 기존 클라우드, 데이터 적재·공유 방식, 동시 사용자, 권한 관리, 과금 단위가 선택에 영향을 줍니다. 서버리스라고 비용·쿼리 최적화 관리가 사라지는 것은 아닙니다.

### Druid와 Pinot

지속적으로 들어오는 이벤트를 집계하고 대화형 응답을 제공하는 요구에서 비교할 수 있습니다. 적재 지연과 질의 지연은 별개의 지표입니다. 데이터가 들어오는 속도, 조회 가능해지는 시점, 집계 결과의 최신성을 함께 측정해야 합니다.

## 🔄 원본 DB에서 분석 DB로 데이터를 옮길 때

주문 서비스와 무거운 분석 쿼리가 같은 자원을 경쟁하면 사용자 요청에 영향을 줄 수 있습니다. 분석용 저장소를 분리할 경우 다음을 설계합니다.

1. **적재 방식**: 배치, 스트리밍, 변경 데이터 캡처(CDC) 중 어떤 방식인가?
2. **최신성**: 몇 초·몇 분·하루의 지연을 허용하는가?
3. **변경 반영**: 수정·삭제·취소 주문을 어떻게 반영하는가?
4. **중복 처리**: 재전송된 이벤트가 집계에 두 번 포함되지 않는가?
5. **스키마 변경**: 새 컬럼이나 타입 변경이 적재와 분석에 어떤 영향을 주는가?
6. **재처리**: 원천에서 다시 적재하고 결과를 검증할 수 있는가?

원본과 분석 사본의 건수·합계가 일치하는지 확인하는 과정도 필요합니다. DB 제품이 중복 제거 기능을 제공하더라도 업무상 같은 이벤트를 식별할 키와 처리 규칙은 설계해야 합니다.

## 💰 분석 비용을 결정하는 요소

| 요소 | 확인할 질문 |
| --- | --- |
| 데이터 스캔 | 필요한 컬럼·기간만 읽는가? |
| 컴퓨팅 | 자원 크기와 실행 시간을 조절할 수 있는가? |
| 동시성 | 대시보드와 배치 쿼리가 서로 영향을 주는가? |
| 저장·복제 | 원본·사본·중간 결과가 얼마나 쌓이는가? |
| 데이터 이동 | 클라우드·지역 간 전송이 발생하는가? |
| 수집·갱신 | 실시간 적재를 유지하는 비용은 얼마인가? |

## ✅ 시리즈를 마치며: 제품보다 요구를 먼저 정하기

전체 시리즈의 제품들은 서로 다른 문제를 해결합니다. 관계형 DB의 트랜잭션, 그래프 DB의 연결 탐색, 검색 엔진의 관련도, 벡터 DB의 유사도, 분석용 DB의 집계를 같은 성능 순위로 비교하기는 어렵습니다.

처음에는 핵심 업무를 충족하는 단순한 구성에서 시작하고, 측정한 병목이나 명확한 기능 요구에 따라 전문 저장소를 추가하는 방식으로 판단할 수 있습니다. 최종 선택은 실제 데이터·쿼리·장애 복구·비용 조건에서 검증해야 합니다.
