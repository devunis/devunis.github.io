LangGraph는 상태와 노드·전이를 이용해 실행 흐름을 구성하는 프레임워크입니다. 여러 역할의 모델·도구 호출을 조율할 수 있지만, 노드가 여러 개라고 모두 자율 에이전트인 것은 아닙니다.

## 🧩 상태·노드·전이

| 요소 | 역할 |
| --- | --- |
| 상태 | 다음 단계에서 필요한 입력·결과 |
| 노드 | 조회·판단·생성 같은 처리 단계 |
| 전이 | 다음에 실행할 노드 결정 |
| 종료 조건 | 반복이 끝나는 기준 |

## 🎁 SenPick에서 살펴볼 설계 관점

SenPick 원본은 감정·상황 기반 선물 추천 서비스입니다. 팀 회고에는 대화 진행, 상황 추출, 추천, 의도 파악의 역할 분리와, 필요한 정보가 갖춰진 경우 추천하도록 제어하는 흐름이 소개되어 있습니다.

위 그림은 공개 설명을 요약한 개념도입니다. 뉴스 검색 서비스의 운영 구조나 정량 성과를 보여주는 자료가 아닙니다.

## 🔄 상태를 어떻게 공유할까?

각 단계가 어떤 필드를 읽고 갱신하는지 명확히 합니다. 병렬 노드가 같은 값을 갱신한다면 병합 규칙이 필요합니다. 무한 재검색을 막을 반복 횟수·종료 기준도 정해야 합니다.

체크포인트를 구성하면 상태를 저장하고 재개할 수 있지만 외부 결제·메시지 같은 부작용까지 자동으로 되돌리지는 않습니다. 재시도 시 중복 작업 방지와 멱등성을 설계합니다.

## ⚡ 응답 속도 최적화

독립적인 I/O 작업을 동시 실행하거나 같은 조회를 캐싱할 수 있습니다. 의존 관계가 있는 작업은 순서를 유지합니다. 타임아웃·취소·부분 실패와 외부 서비스의 요청 한도를 함께 처리해야 합니다.

성능은 노드별 지연과 전체 요청의 P95 등을 측정해 판단합니다. 이 글에는 근거 없는 CTR·정확도·응답 시간·오류율 개선 수치를 제시하지 않습니다.

## ✅ 설계 점검

- 필요한 정보가 부족할 때 추가 질문하는가?
- 노드의 책임과 상태 변경이 명확한가?
- 도구 실패·사용자 취소·재시도를 처리하는가?
- 반복과 외부 호출의 비용을 제한하는가?
- 검색 결과의 출처와 권한을 유지하는가?
