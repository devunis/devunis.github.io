FAISS와 Qdrant는 모두 벡터 검색에 사용할 수 있지만 제공 범위가 다릅니다. 이 글은 기능과 운영 책임을 비교하며, 근거 없는 벤치마크 결과나 프로젝트의 이전 이력을 주장하지 않습니다.

## 📊 기능보다 먼저 구조를 비교

| 관점 | FAISS | Qdrant |
| --- | --- | --- |
| 기본 형태 | 애플리케이션에 포함하는 검색 라이브러리 | 벡터와 메타데이터를 관리하는 DB |
| 데이터 접근 | 인덱스를 호출하는 코드 구성 | API·클라이언트와 서버 또는 지원 배포 구성 |
| 필터·메타데이터 | 선택한 인덱스·별도 구현에 따라 구성 | payload와 필터 기능 제공 |
| 운영 책임 | 저장·서비스·동시성·복구 등을 직접 조합 | DB의 저장·분산 기능과 운영 설정 검토 |

FAISS에도 ID 선택 등 검색을 제한하는 기능이 있으므로 “필터가 전혀 없다”는 설명은 피합니다. Qdrant의 일반적인 메타데이터 필터와 같은 제공 범위인지는 따로 확인합니다.

## 🔎 검색 품질은 제품 이름으로 정해지지 않는다

정확 검색과 근사 검색의 인덱스를 구분합니다. 임베딩, 거리 함수, 인덱스·탐색 설정, 필터가 결과에 영향을 줍니다. 동일한 조건의 Recall@K와 지연·처리량을 함께 측정해야 합니다.

## ⚡ 측정할 항목

- 인덱스 생성 시간과 메모리·디스크 사용량.
- 검색 지연의 평균·P95와 동시 요청 처리량.
- 필터가 있는 검색의 결과 수·관련성.
- 데이터 수정·삭제가 반영되는 시점.
- 저장·재시작·백업 복구의 동작.

캐시 적중 여부와 네트워크 구간도 구분합니다. 응답 시간을 특정 수치로 보장하거나 서로 다른 인덱스 설정의 결과로 제품 전체를 평가하지 않습니다.

## ✅ 선택 예시

기존 애플리케이션에서 인덱스를 직접 관리하고 서비스 계층도 구현할 수 있다면 FAISS를 검토할 수 있습니다. 벡터·필터·조회 API와 DB 운영 기능을 함께 활용하려면 Qdrant를 검토할 수 있습니다. 어느 쪽도 개인 실험이나 특정 데이터 규모에만 제한되지 않습니다.
