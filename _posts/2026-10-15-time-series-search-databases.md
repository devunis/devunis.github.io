> 데이터베이스 종류와 대표 제품을 비교하는 7편 시리즈의 5편입니다. 각 제품명은 공식 소개 또는 문서로 연결됩니다.

서버의 CPU 사용률을 기간별로 집계하는 일과, 상품 설명에서 관련 문서를 찾는 일은 조회 방식이 다릅니다. 이 글에서는 시간 축에 특화된 제품 4개와 검색 중심 제품 3개를 비교합니다.

## ⏱️ 시계열 DB: 시간에 따라 쌓이는 값

시계열 데이터는 시각과 값, 구분용 속성으로 구성됩니다. 예를 들면 `측정 시각 + 서버 이름 + CPU 사용률`입니다.

자주 필요한 작업은 최근 구간 조회, 시간 단위 집계, 보존 기간 관리, 오래된 데이터의 요약입니다. 같은 제품이라도 센서 원시 데이터와 모니터링 메트릭의 수집·조회 요구는 다를 수 있습니다.

| 제품 | 특징·강점 | 검토할 사용처 | 주의점 |
| --- | --- | --- | --- |
| [InfluxDB](https://docs.influxdata.com/) | 시간 중심 데이터 수집·조회와 시계열 생태계 | 센서, 이벤트, 운영 지표 | 주요 버전별 엔진·질의 언어·API 차이 확인 |
| [TimescaleDB](https://docs.timescale.com/api/latest/hypertable/create_hypertable/) | PostgreSQL 확장, hypertable과 시간 기반 파티셔닝 | 시계열과 회원·장비 같은 관계형 데이터 결합 | 확장 버전·기능의 배포 조건과 데이터 보존·집계 설정 확인 |
| [QuestDB](https://questdb.com/docs/) | SQL과 시간 중심 조회 기능 | 금융 틱, 이벤트·센서 데이터 분석 | 입력 순서, 시간 컬럼, 지원 프로토콜·SQL 범위 확인 |
| [VictoriaMetrics](https://docs.victoriametrics.com/) | 메트릭 수집·저장·조회, Prometheus 생태계 연계 | 인프라·애플리케이션 모니터링 | 라벨 카디널리티, 보존 기간, 단일 노드·클러스터 구조 확인 |

### TimescaleDB는 관계형 DB와 함께 이해

TimescaleDB는 독립된 비관계형 DB로만 분류하기보다 PostgreSQL에 시계열 기능을 추가하는 확장으로 이해하는 것이 정확합니다. 시간 데이터와 장비·고객 테이블을 SQL로 함께 다루는 요구에서 비교할 수 있습니다.

### 라벨 카디널리티가 중요한 이유

서버 이름·지역처럼 값을 구분하는 속성의 조합이 많아지면 시계열 수도 늘어납니다. 사용자 ID나 요청 ID를 무분별하게 메트릭 라벨로 넣으면 메모리·인덱스·조회 비용이 커질 수 있습니다. 어떤 값은 메트릭보다 로그나 이벤트에 저장하는 편이 적합합니다.

## 🔎 검색 중심 저장소: 문서의 관련도를 찾기

검색 엔진은 단순히 문자열이 포함되었는지만 확인하지 않습니다. 텍스트를 분석하고, 단어에서 문서로 접근하는 **역색인** 등을 통해 검색과 관련도 계산을 수행합니다.

한국어 검색에서는 분석기, 사용자 사전, 띄어쓰기, 동의어 설계가 검색 품질에 영향을 줍니다. 인덱스를 만들었다는 사실만으로 좋은 검색 결과가 보장되지는 않습니다.

| 제품 | 특징·강점 | 검토할 사용처 | 주의점 |
| --- | --- | --- | --- |
| [Elasticsearch](https://www.elastic.co/elasticsearch) | 분산 검색·분석 엔진, 전문·벡터 검색 등 제공 | 상품·문서 검색, 로그 분석 | 매핑·분석기·샤드 설계, 메모리와 색인 지연 관리 |
| [OpenSearch](https://docs.opensearch.org/latest/) | Elasticsearch 7.10.2 계열에서 분기한 검색·분석 프로젝트 | 전문 검색, 로그·관측 데이터 분석 | 최신 Elasticsearch와 API·플러그인·기능이 같지 않음 |
| [Apache Solr](https://solr.apache.org/) | Lucene 기반 검색 서버, 패싯·검색 기능과 SolrCloud | 전문 검색, 필터·패싯 중심 검색 서비스 | 스키마·분석기와 분산 구성 운영 확인 |

### Elasticsearch와 OpenSearch는 완전한 대체 관계일까?

공통된 출발점이 있지만 독립적으로 발전했습니다. 마이그레이션 시 인덱스 형식, 클라이언트, 플러그인, 보안 설정, 질의 동작을 확인해야 합니다. 라이선스 역시 현재 사용하는 배포판과 버전의 조건을 확인해야 합니다.

### 검색용 사본과 원본 DB

주문 원본은 관계형 DB에 저장하고 상품 검색용 문서를 검색 엔진에 전달할 수 있습니다. 이때 다음을 설계해야 합니다.

1. 원본 변경이 검색에 반영되기까지의 지연.
2. 전송 실패 시 재시도와 중복 처리.
3. 삭제 데이터와 권한 변경의 반영.
4. 인덱스 전체 재구축과 전환 방법.

검색 엔진의 문서 저장 기능과, 주문·결제 업무가 요구하는 여러 레코드의 트랜잭션 보장은 구분해야 합니다.

## ✅ 어떤 계열을 검토할까?

| 핵심 질문 | 검토할 계열 |
| --- | --- |
| 최근 1시간 CPU 평균은? | 시계열·메트릭 저장소 |
| 센서 값을 시간 구간별로 집계하려면? | 시계열 DB 또는 분석용 DB |
| 상품명 오타·동의어를 고려해 검색하려면? | 검색 엔진 |
| 로그 본문 검색과 필드별 집계를 함께 하려면? | 검색·로그 분석 엔진 |
| 키워드와 의미 검색을 결합하려면? | 검색 엔진의 벡터 기능 또는 벡터 DB |

로그에 시간이 있다고 반드시 시계열 DB만 사용하는 것은 아닙니다. 시간 범위 집계가 중심인지, 본문 검색이 중심인지, 장기 대량 분석이 중심인지에 따라 비교 대상이 달라집니다.
