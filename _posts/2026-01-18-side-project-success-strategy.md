사이드 프로젝트를 설명할 때는 무엇을 만들었는지와 실제 확인한 결과를 구분해야 합니다. 이 글은 특정 기간·사용자 수·성과를 보장하는 성공 공식이 아니라, 작은 프로젝트를 정리하는 방법입니다.

## 🎯 범위를 정하기

해결할 문제, 사용할 사람, 핵심 사용자 흐름을 한 문장씩 적습니다. 선물 추천 서비스라면 상황 입력 → 대화 → 상품 추천을 먼저 완성하고, 부가 기능은 별도로 관리할 수 있습니다.

MVP의 기간은 요구와 팀 상황에 따라 다릅니다. 임의의 개발 기간을 실제 프로젝트 이력으로 쓰지 않습니다.

## 🛠️ 기술 선택을 설명하기

| 판단 기준 | 기록할 질문 |
| --- | --- |
| 제품 요구 | 관리자 기능, API, 모바일 중 무엇이 필요한가? |
| 팀 경험 | 운영·디버깅할 수 있는 기술인가? |
| 데이터 | 관계·검색·파일·모델을 어떻게 연결하는가? |
| 배포 | 비밀 값, 백업, 장애 대응은 누가 맡는가? |

기술의 이름보다 선택 이유와 대안을 적습니다. SenPick의 원본은 Django 기반 선물 추천 프로젝트이며, 기술 뉴스 추천이나 FastAPI 사례로 소개하지 않습니다.

## 📝 README와 회고 구성

1. 문제와 사용자 흐름.
2. 실행 조건·설치·환경변수 예시.
3. 전체 구조와 실제 담당 범위.
4. 구현한 기능과 미완성 기능.
5. 테스트·검증 방법과 한계.
6. 다음 개선 과제.

개인 기여와 팀의 결과를 나눠 적고, 다른 프로젝트의 기술 스택·출시 여부를 섞지 않습니다. Tongue Twist의 블로그 소개는 Streamlit 음성 앱이므로 근거 없는 Android·Google Play 출시 이력으로 바꾸지 않습니다.

## ⚡ 응답 속도 개선을 어떻게 쓸까?

측정값이 없다면 “독립 요청의 동시 실행과 캐싱을 검토했다”처럼 실제 작업 범위를 씁니다. 적용한 코드가 있다면 해당 변경을 연결합니다. 결과를 주장하려면 같은 환경에서 지연·오류율·부하와 측정 방법을 기록해야 합니다.

| 피할 표현 | 근거에 맞는 기록 방법 |
| --- | --- |
| 근거 없는 개선율·정확도 | 구현 방법, 평가 계획, 확인한 제약 |
| 팀 전체 결과를 개인 성과로 표기 | 맡은 기능과 협업 경계 |
| 예제 코드를 운영 코드로 소개 | 설명용 예제임을 표시 |
| 계획한 기능을 완료로 표기 | 구현·진행·검토 상태 구분 |

## ✅ 공개 전 확인

저장소·실행 명령·프로젝트 링크를 확인합니다. 성능 수치에는 재현 가능한 기록을 연결하고, 측정하지 않은 효과는 기대나 검토 과제로 적습니다. 사용자를 확보하거나 출시했다고 쓰려면 해당 사실을 확인할 수 있어야 합니다.
